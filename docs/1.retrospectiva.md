# Retrospectiva — Pipeline de Extração de Dados

## O que foi construído

Um pipeline de extração de dados do sistema da oficina, que acessa o sistema via navegador automatizado (Selenium), exporta os dados em CSV e registra cada execução em um log histórico.

## Decisões técnicas tomadas

### 1. Selenium para extração
O sistema da oficina não tem API. A solução foi automatizar o navegador para simular o uso humano: login, navegação até o relatório e clique no botão de exportar CSV.

### 2. Separação selenium / http
A pasta `src/scripts_extracao/selenium/` existe para scripts de extração visual (com navegador), pensando que no futuro haverá `src/scripts_http/` com extração direta via requisições HTTP — mais rápido e adequado para produção.

### 3. Variáveis de ambiente com `find_dotenv()`
As credenciais ficam no `.env` na raiz do projeto. Usar `find_dotenv()` garante que o arquivo seja encontrado independente de onde o script é executado — ele sobe os diretórios até encontrar o `.env`.

### 4. Nomenclatura em português descritivo
Todas as variáveis e funções foram padronizadas em português para facilitar a leitura e apresentação para a banca. Ex: `DIRETORIO_DESTINO`, `aguardar_download_e_renomear_arquivo`, `executar_extracao`.

### 5. `main.py` com `importlib` em vez de `subprocess`
A primeira versão usava `subprocess` para rodar cada script como um processo separado. O problema: não daria para compartilhar um único logger entre todos os scripts.

A solução foi usar `importlib.util` para carregar cada script como módulo Python dentro do mesmo processo, permitindo passar o logger como parâmetro.

### 6. Injeção de dependência no logger
Os scripts não sabem como o log é feito. Eles recebem um `logger` como parâmetro e chamam `logger.registrar_sucesso(...)` ou `logger.registrar_erro(...)`.

Hoje esse logger grava em CSV. No futuro, dentro do Airflow, bastaria criar um `LoggerAirflow` com os mesmos dois métodos e injetá-lo — sem alterar nenhum script de extração.

### 7. Protocol em vez de herança
O contrato do logger é definido como um `Protocol` (equivalente a uma interface em outras linguagens). Isso significa que qualquer classe com os métodos `registrar_sucesso` e `registrar_erro` automaticamente satisfaz o contrato, sem precisar herdar explicitamente.

### 8. Log em CSV com append
O arquivo `historico_extracoes.csv` nunca é sobrescrito — cada execução adiciona linhas ao final. Isso cria um histórico completo de todas as extrações, com timestamp, entidade, status, número de registros retornados e caminho do arquivo gerado.

### 9. Conflito de nome `src/selenium/`
O diretório foi renomeado para `src/scripts_extracao/selenium/` porque o Python confundia o nome da pasta com o pacote instalado `selenium` na hora do import via `importlib`.

## Fluxo de uma execução

```
python src/main.py
    │
    ├── calcula período (domingo anterior → sábado anterior)
    ├── instancia LoggerCSV(metodo="selenium")
    │
    └── para cada script em scripts_extracao/selenium/:
        │
        ├── abre Chrome
        ├── faz login no sistema
        ├── navega até o relatório
        ├── preenche filtro de data (se aplicável)
        ├── dispara exportarCSV() via JavaScript
        ├── aguarda download e renomeia para YYYY-MM-DD.csv
        ├── logger.registrar_sucesso(entidade, caminho, registros, detalhes)
        └── fecha Chrome
```

## Regras de período do filtro de data

### Por que filtro de data?

Duas das seis entidades extraídas — **ordens de serviço** e **itens de ordens de serviço** — são transacionais: novos registros surgem a cada dia de operação. Extrair tudo a cada execução seria redundante e ineficiente. As outras quatro entidades (clientes, motocicletas, produtos, serviços) são cadastros estáticos extraídos completos a cada execução.

### Por que filtrar por data de saída e não de entrada?

O sistema ERP oferece três opções de filtro: entrada, previsão e saída. Filtrar por **data de entrada** faria com que cada OS aparecesse na extração da semana em que foi aberta — independente de estar finalizada ou não. Isso significa que o DW teria registros de OS permanentemente "abertas", mesmo que já tivessem sido concluídas semanas depois.

Filtrar por **data de saída** garante que uma OS só entra no DW quando está finalizada, com todos os seus dados completos — valor total, itens, serviços e status de encerramento. OS ainda abertas simplesmente não aparecem até serem concluídas, o que é o comportamento correto para análise histórica.

### Por que semana fechada (domingo → sábado)?

A oficina opera de segunda a sábado. Usar uma janela de "últimos 7 dias a partir de hoje" criaria um período inconsistente dependendo do dia da execução — e em caso de falha, dias seriam perdidos permanentemente.

A semana fechada garante:
- **Período fixo e completo**: sempre domingo anterior → sábado anterior, cobrindo toda a semana de operação
- **Idempotência**: rodar o script duas vezes na mesma semana extrai exatamente o mesmo intervalo
- **Recuperação de falhas**: se o cron falhar, rodar manualmente qualquer dia da semana seguinte ainda captura a semana perdida

### Cálculo no código

```python
hoje = date.today()
ultimo_sabado = hoje - timedelta(days=(hoje.weekday() + 2) % 7 or 7)
data_inicio = ultimo_sabado - timedelta(days=6)  # domingo
data_fim = ultimo_sabado                          # sábado
```

### Modos de execução

```bash
python src/main.py --carga-inicial   # carga_completa — sem filtro de data, sistema retorna tudo
python src/main.py                   # incremental — semana anterior (domingo → sábado)
```

No modo `--carga-inicial` os campos de data ficam em branco no formulário do ERP, que por padrão retorna todo o histórico disponível.

## Rastreabilidade das extrações

O logger registra cada execução em `data/logs/historico_extracoes.csv`. A coluna `detalhes` armazena um JSON que identifica o tipo de execução e, quando aplicável, o período consultado:

```json
// cadastros (carga completa)
{"tipo": "carga_completa"}

// transacionais (carga completa)
{"tipo": "carga_completa", "periodo_consulta": {"data_inicio": null, "data_fim": null}}

// transacionais (incremental)
{"tipo": "incremental", "periodo_consulta": {"data_inicio": "01/06/2026", "data_fim": "07/06/2026"}}
```

Usar JSON na coluna permite adicionar novas propriedades no futuro sem alterar o schema do CSV, e facilita o parsing programático sem depender de strings frágeis.

## Transformação

Os scripts de transformação leem os CSVs extraídos, padronizam nomes de colunas, convertem tipos e devolvem um DataFrame pronto para ser carregado. Cada entidade tem seu próprio script em `src/scripts_transformacao/`.

### Desafios e soluções

**1. Campo `ano` da motocicleta no formato `"14|15"`**

O ERP armazena o ano no formato `ano_fabricacao|ano_modelo` usando dois dígitos. Para fins de compatibilidade de peças o que importa é o ano do modelo (segundo valor). A solução foi criar `extrair_ano_modelo()` que extrai o segundo número e converte para 4 dígitos usando a regra: `>= 40 → 1900s`, `< 40 → 2000s`. Exemplo: `"14|15"` → `2015`, `"89|90"` → `1990`.

**2. Contagem de registros incorreta no logger**

O campo `obs` de clientes pode conter quebras de linha dentro de aspas. O contador `sum(1 for _ in open(caminho, "rb"))` contava essas quebras como linhas extras, inflando o número registrado no log. A solução foi usar `csv.reader` com `delimiter=";"`, que respeita o protocolo CSV e trata campos entre aspas como um único registro.

**3. Inferência do tipo de item de OS (`produto` ou `servico`)**

Os itens de OS não têm um campo de tipo na exportação. A solução foi fazer um lookup cruzando `id + descricao` simultaneamente nas tabelas de produtos e de serviços — pois como são tabelas diferentes no ERP, os IDs podem se repetir entre elas. O match exige que tanto o ID quanto a descrição coincidam (normalizado em uppercase com strip).

**4. Registro de exemplo do ERP contaminando os dados**

O sistema cria automaticamente um cliente (id=1) e uma OS (id=1) de exemplo. Esse cliente tinha uma OS aberta em 2016 e fechada em 2024, fora do range do `dim_data`. A solução foi filtrar `nk_cliente != 1` e `nk_ordem_de_servico != 1` na transformação.

**5. OS sem itens no CSV de itens**

O relatório de itens do ERP inclui linhas para OS que ainda não têm produtos ou serviços lançados (AGENDADO, NEGOCIACAO). Essas linhas têm `Descricao Produtos Servicos` vazio. A solução foi descartar linhas com `descricao` nula na transformação — elas entrarão normalmente quando a OS for finalizada em extrações futuras.

## Carregamento

Os scripts de carregamento leem os CSVs transformados e fazem upsert nas tabelas do DW via `supabase-py`. A ordem de execução é obrigatória por causa das foreign keys: `dim_cliente` → `dim_motocicleta` → `fact_ordem_de_servico` → `fact_item_os`.

### Decisões de design

**Upsert por chave natural nas dimensões**

`dim_cliente` e `dim_motocicleta` têm constraint `UNIQUE` em `nk_cliente` e `nk_motocicleta` respectivamente. Isso permite upsert idempotente — rodar o script duas vezes não duplica registros.

**Upsert por `nk_ordem_de_servico` na fact**

`fact_ordem_de_servico` recebeu uma constraint `UNIQUE (nk_ordem_de_servico)` via `ALTER TABLE` para permitir o mesmo padrão de upsert. Sem ela, cada execução criaria duplicatas.

**Filtro de OS finalizadas no carregamento**

O script `carregar_ordens_de_servico.py` filtra `dt_saida.notna()` antes de carregar. OS ainda abertas (sem data de saída) são ignoradas nessa execução e entrarão no DW quando forem finalizadas em extrações futuras. Isso funciona tanto para a carga inicial quanto para cargas incrementais sem nenhuma lógica condicional adicional.

**Idempotência de `fact_item_os`**

`fact_item_os` não tem chave natural única (uma OS pode ter dois itens do mesmo produto). A solução foi: antes de inserir, deletar todos os itens existentes para as OS do lote atual. Garante que uma re-execução não duplica itens.

**Lookup de SK em bulk**

A resolução de chaves substitutas (sk_cliente, sk_motocicleta, sk_ordem_servico) é feita com uma única query por entidade usando filtro `in_()` — não uma query por linha. Isso evita N+1 queries e mantém a carga eficiente mesmo com centenas de registros.

### Desafios e soluções

**1. NaN não serializável em JSON**

Ao converter o DataFrame para lista de dicts via `to_dict()`, colunas numéricas com valores ausentes produzem `float('nan')`, que não é válido em JSON. A solução foi `df.astype(object).where(pd.notnull(df), None)` antes do `to_dict()`, que converte NaN para `None` (serializado como `null`).

**2. Inteiros virando float no dict (`15` → `15.0`)**

Quando uma coluna tem valores inteiros e `None`, o pandas a armazena como `float64` (ex: `15.0`). Ao passar para o Postgres, colunas `INTEGER` rejeitam `"15.0"`. A solução foi a função `sanitizar()`, aplicada a cada registro antes do upsert: floats que são inteiros exatos (`v == int(v)`) são convertidos para `int`.

**3. `dim_data` com range insuficiente**

O `dim_data` foi populado inicialmente de 2024 a 2040. O carregamento falhou para uma OS com `data_inclusao` em 2016 — era a OS de exemplo do ERP (id=1). O problema foi resolvido filtrando esse registro na transformação, sem necessidade de estender o range do `dim_data`.

**4. CSV lido sem `dtype=str` causava `"2015.0"` em VARCHAR(4)**

O campo `ano` de motocicletas era lido pelo script de carregamento sem `dtype=str`, fazendo o pandas inferir o tipo como float. Resultado: `"2015"` virava `2015.0`, que tem 6 caracteres e violava o `VARCHAR(4)`. A solução foi forçar `dtype=str` na leitura dos CSVs em todos os scripts de carregamento.
