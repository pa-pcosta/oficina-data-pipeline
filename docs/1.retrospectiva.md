# Retrospectiva — Pipeline de Extração de Dados

## O que foi construído

Um pipeline de extração de dados do sistema da oficina, que acessa o sistema via navegador automatizado (Selenium), exporta os dados em CSV e registra cada execução em um log histórico.

## Decisões técnicas tomadas

### 1. Selenium para extração
O sistema da oficina não tem API. A solução foi automatizar o navegador para simular o uso humano: login, navegação até o relatório e clique no botão de exportar CSV.

### 2. Separação selenium / http
A pasta `src/scripts_selenium/` existe para scripts de extração visual (com navegador), pensando que no futuro haverá `src/scripts_http/` com extração direta via requisições HTTP — mais rápido e adequado para produção.

### 3. Variáveis de ambiente com `find_dotenv()`
As credenciais ficam no `.env` na raiz do projeto. Usar `find_dotenv()` garante que o arquivo seja encontrado independente de onde o script é executado — ele sobe os diretórios até encontrar o `.env`.

### 4. Nomenclatura em português descritivo
Todas as variáveis e funções foram padronizadas em português para facilitar a leitura e apresentação para a banca. Ex: `DIRETORIO_DESTINO`, `aguardar_download_e_renomear_arquivo`, `executar_extracao`.

### 5. `main.py` com `importlib` em vez de `subprocess`
A primeira versão usava `subprocess` para rodar cada script como um processo separado. O problema: não daria para compartilhar um único logger entre todos os scripts.

A solução foi usar `importlib.util` para carregar cada script como módulo Python dentro do mesmo processo, permitindo passar o logger como parâmetro.

### 6. Injeção de dependência no logger
Os scripts não sabem como o log é feito. Eles recebem um `logger` como parâmetro e chamam `logger.registrar_sucesso(...)` ou `logger.registrar_erro(...)`.

Hoje esse logger grava em CSV. No futuro, dentro do Airflow, bastaria criar um `LoggerAirflow` com os mesmos dois métodos e injetá-lo — sem alterar nenhum script de extração.

### 7. Protocol em vez de herança
O contrato do logger é definido como um `Protocol` (equivalente a uma interface em outras linguagens). Isso significa que qualquer classe com os métodos `registrar_sucesso` e `registrar_erro` automaticamente satisfaz o contrato, sem precisar herdar explicitamente.

### 8. Log em CSV com append
O arquivo `historico_extracoes.csv` nunca é sobrescrito — cada execução adiciona linhas ao final. Isso cria um histórico completo de todas as extrações, com timestamp, entidade, status, número de registros retornados e caminho do arquivo gerado.

### 9. Conflito de nome `src/selenium/`
O diretório foi renomeado para `src/scripts_selenium/` porque o Python confundia o nome da pasta com o pacote instalado `selenium` na hora do import via `importlib`.

## Fluxo de uma execução

```
python src/main.py
    │
    ├── calcula período (domingo anterior → sábado anterior)
    ├── instancia LoggerCSV(metodo="selenium")
    │
    └── para cada script em scripts_selenium/:
        │
        ├── abre Chrome
        ├── faz login no sistema
        ├── navega até o relatório
        ├── preenche filtro de data (se aplicável)
        ├── dispara exportarCSV() via JavaScript
        ├── aguarda download e renomeia para YYYY-MM-DD.csv
        ├── logger.registrar_sucesso(entidade, caminho, registros, detalhes)
        └── fecha Chrome
```

## Regras de período do filtro de data

### Por que filtro de data?

Duas das seis entidades extraídas — **ordens de serviço** e **itens de ordens de serviço** — são transacionais: novos registros surgem a cada dia de operação. Extrair tudo a cada execução seria redundante e ineficiente. As outras quatro entidades (clientes, motocicletas, produtos, serviços) são cadastros estáticos extraídos completos a cada execução.

### Por que filtrar por data de saída e não de entrada?

O sistema ERP oferece três opções de filtro: entrada, previsão e saída. Filtrar por **data de entrada** faria com que cada OS aparecesse na extração da semana em que foi aberta — independente de estar finalizada ou não. Isso significa que o DW teria registros de OS permanentemente "abertas", mesmo que já tivessem sido concluídas semanas depois.

Filtrar por **data de saída** garante que uma OS só entra no DW quando está finalizada, com todos os seus dados completos — valor total, itens, serviços e status de encerramento. OS ainda abertas simplesmente não aparecem até serem concluídas, o que é o comportamento correto para análise histórica.

### Por que semana fechada (domingo → sábado)?

A oficina opera de segunda a sábado. Usar uma janela de "últimos 7 dias a partir de hoje" criaria um período inconsistente dependendo do dia da execução — e em caso de falha, dias seriam perdidos permanentemente.

A semana fechada garante:
- **Período fixo e completo**: sempre domingo anterior → sábado anterior, cobrindo toda a semana de operação
- **Idempotência**: rodar o script duas vezes na mesma semana extrai exatamente o mesmo intervalo
- **Recuperação de falhas**: se o cron falhar, rodar manualmente qualquer dia da semana seguinte ainda captura a semana perdida

### Cálculo no código

```python
hoje = date.today()
ultimo_sabado = hoje - timedelta(days=(hoje.weekday() + 2) % 7 or 7)
data_inicio = ultimo_sabado - timedelta(days=6)  # domingo
data_fim = ultimo_sabado                          # sábado
```

### Modos de execução

```bash
python src/main.py --carga-inicial   # carga_completa — sem filtro de data, sistema retorna tudo
python src/main.py                   # incremental — semana anterior (domingo → sábado)
```

No modo `--carga-inicial` os campos de data ficam em branco no formulário do ERP, que por padrão retorna todo o histórico disponível.

## Rastreabilidade das extrações

O logger registra cada execução em `data/logs/historico_extracoes.csv`. A coluna `detalhes` armazena um JSON que identifica o tipo de execução e, quando aplicável, o período consultado:

```json
// cadastros (carga completa)
{"tipo": "carga_completa"}

// transacionais (carga completa)
{"tipo": "carga_completa", "periodo_consulta": {"data_inicio": null, "data_fim": null}}

// transacionais (incremental)
{"tipo": "incremental", "periodo_consulta": {"data_inicio": "01/06/2026", "data_fim": "07/06/2026"}}
```

Usar JSON na coluna permite adicionar novas propriedades no futuro sem alterar o schema do CSV, e facilita o parsing programático sem depender de strings frágeis.
